# StackView

StackView — сервис обратной связи для персонального лендинга разработчика.

Задача проекта: принять сообщение с сайта (имя, телефон, email, комментарий), аккуратно обработать его на бэкенде и помочь владельцу сайта быстрее ответить. Для этого сервис проверяет данные, защищается от спама по IP, при возможности обогащает обращение через AI (категория, тональность, черновик ответа), отправляет письма владельцу и отправителю и сохраняет результат в PostgreSQL. Рядом с API есть простой лендинг с формой, OpenAPI-документация и эндпоинт метрик — чтобы было удобно смотреть, как всё работает end-to-end.

Проект сделан как полноценный небольшой backend с понятной архитектурой.

## 1. Как запустить проект

### Требования

- Python 3.12–3.14
- Poetry
- PostgreSQL (**обязателен** — без БД приложение не стартует корректно)
- SMTP — **не обязателен** для локального `APP_ENV=development`: сервис запустится, форма примет обращение, но `email_sent` будет `false`
- Ключ AI (Groq/OpenAI) — **не обязателен**: без ключа форма тоже принимается, `ai_available=false`

### Установка

```bash
git clone https://github.com/simbarilion/StackView.git
cd StackView
poetry install
cp .env.example .env
```

Заполните `.env` по примеру `.env.example`.

### Миграции и seed

```bash
poetry run alembic upgrade head
poetry run seed
```

`seed` записывает демо-обращения, если таблица БД пуста. Если записи уже есть — seed пропускается.

### Запуск

```bash
make run
# или:
poetry run uvicorn app.main:app --reload
```

- Сайт: http://127.0.0.1:8000/
- Docs: http://127.0.0.1:8000/api/docs

### Полезные команды

```bash
make test
make lint
make format
```

### Переменные окружения

| Группа | Переменные |
|--------|------------|
| Приложение | `APP_NAME`, `APP_ENV` (`development` / `production`), `APP_DEBUG`, `APP_HOST`, `APP_PORT`, `CORS_ORIGINS` |
| Логи | `LOG_LEVEL`, `LOG_DIR`, `LOG_FILE`, `REQUEST_LOG_FILE` |
| Файловые данные | `DATA_DIR` (сюда пишется rate limit) |
| БД локально | `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT` |
| БД на Render | `DATABASE_URL` (подставляет Render) |
| Rate limit | `RATE_LIMIT_REQUESTS`, `RATE_LIMIT_WINDOW_SECONDS` |
| SMTP | `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_USE_TLS`, `SMTP_USE_SSL`, `MAIL_FROM`, `MAIL_TO_OWNER` |
| AI | `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL`, `AI_TIMEOUT_SECONDS`, `AI_ENABLED` |

Пример SMTP (Yandex, порт 465):

```env
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_USE_TLS=false
SMTP_USE_SSL=true
SMTP_USERNAME=...
SMTP_PASSWORD=...
MAIL_FROM=...
MAIL_TO_OWNER=...
```

Пример AI (Groq через OpenAI-совместимый SDK):

```env
OPENAI_API_KEY=gsk_...
OPENAI_BASE_URL=https://api.groq.com/openai/v1
OPENAI_MODEL=llama-3.3-70b-versatile
AI_ENABLED=true
```

Поведение почты:

- `development` + SMTP не настроен → обращение принимается, `email_sent=false`
- `production` + SMTP не настроен → **502** `email_not_configured`

## 2. Стек технологий

### Backend

| Область | Технологии |
|---------|------------|
| Язык | Python 3.12+ |
| API-сервер | FastAPI, Uvicorn |
| Валидация и сериализация | **Pydantic** (модели запроса/ответа), **pydantic-settings** (конфиг из `.env`) |
| Проверка email | email-validator |
| БД | PostgreSQL, SQLAlchemy 2 (async + asyncpg), Alembic, psycopg2 (для миграций) |
| Почта | aiosmtplib, Jinja2 (HTML/текст писем) |
| AI | официальный пакет **openai** (`AsyncOpenAI`) |
| Качество кода | Ruff, mypy, pre-commit, pytest, pytest-asyncio |
| Сборка и запуск | Poetry (зависимости), Docker (образ для Render) |

**httpx**: пакет `openai` сам использует httpx для HTTP-запросов к API модели. Отдельно подключать httpx не нужно: он приходит как зависимость клиента openai.

### AI

- Библиотека: **openai** (`AsyncOpenAI`)
- Провайдер в рабочем примере: **Groq** (через `OPENAI_BASE_URL`)
- Модель: `llama-3.3-70b-versatile`
- Формат ответа модели: JSON (`response_format: json_object`)

### Frontend

Лендинг отдаётся FastAPI-приложением:

- HTML собирается шаблоном Jinja2 (`landing.html`)
- Внешний вид — обычный CSS
- Поведение формы — небольшой скрипт на чистом JavaScript без React/Vue: браузер отправляет JSON на тот же backend (`POST /api/contact`) и показывает результат на странице

Отдельный SPA не делался специально: проще деплой одним сервисом.

### Почему выбран такой стек

**FastAPI** даёт типизированные эндпоинты, встроенную OpenAPI-документацию и удобный `Depends` — это хорошо стыкуется с требованием "понятный REST API + docs".

**Pydantic** используется и для входа (валидация/санитизация формы), и для выхода (стабильный JSON-контракт).

**PostgreSQL + SQLAlchemy 2 + Alembic** нужны, потому что обращения и метрики — полноценные данные, а не временный лог: миграции фиксируют схему, async-движок не блокирует event loop на I/O.

**Файловый rate limit** вместо Redis выбран осознанно: состояние можно посмотреть в `data/rate_limit.json`, его легко сбросить, нет лишнего сервиса в инфраструктуре. Для высокой нагрузки возможно использовать Redis.

**Пакет openai + `OPENAI_BASE_URL`** позволяет не привязываться жёстко к одному сервису: тот же код используется в OpenAI, Groq или другой OpenAI-compatible API. В проекте это пригодилось, когда у OpenAI не было квоты, а Groq оставался бесплатным для тестов.

**Jinja2** уже использовался для писем; им же отрендерен лендинг — один стек шаблонов, без отдельного фронтенд-билда.

**Poetry и Docker** разделяют роли: Poetry фиксирует зависимости для разработки и CI, Docker даёт воспроизводимый запуск на Render (`alembic` + `uvicorn` в одном образе).

## 3. Архитектура

### Структура проекта

```text
StackView/
├── app/
│   ├── api/              # HTTP-слой: роутеры и Depends

│   ├── schemas/          # Pydantic-схемы API
│   ├── services/         # бизнес-логика (contact, ai, email, rate_limit)
│   ├── scripts/          # seed
│   ├── static/           # css и js лендинга
│   ├── templates/        # HTML лендинга и шаблоны писем
│   └── main.py           # создание приложения, lifespan, static
├── alembic/              # миграции БД

```

Каталог `data/` — рабочая папка приложения: сюда пишется счётчик rate limit. В git обычно лежит только `.gitkeep`, сами JSON-файлы не коммитятся.

### Паттерны

**Слоистая архитектура (Layered Architecture).**

Приложение разделено на независимые слои с чёткими зонами ответственности:

* Router — принимает HTTP-запрос, выполняет валидацию и передаёт управление сервису.
* Service — содержит бизнес-логику и управляет сценарием выполнения (генерация AI-резюме → отправка email → сохранение данных).
* Repository — отвечает только за работу с базой данных и не содержит бизнес-логики.

Такое разделение делает код проще для тестирования, сопровождения и расширения, поскольку изменения в одном слое минимально влияют на остальные.

**Dependency Injection.**

Для внедрения зависимостей используется встроенный механизм FastAPI (Depends).

Благодаря этому роутеры не создают объекты вручную (EmailService(), OpenAIService()), а получают уже готовые экземпляры.

Это уменьшает связанность компонентов и облегчает замену зависимостей при тестировании.

**Разделение моделей API и базы данных.**

Используются разные модели для разных задач:

* Pydantic — описание входных и выходных данных API;
* SQLAlchemy — описание структуры таблиц базы данных.

Такое разделение предотвращает утечку внутренней структуры БД во внешний API и позволяет независимо развивать публичный контракт и модель хранения данных.

**Единый формат обработки ошибок.**

Все ошибки API возвращаются в едином формате:

{
  "code": "...",
  "message": "...",
  "details": "...",
  "request_id": "..."
}

Единый контракт ошибок упрощает обработку ответов на стороне клиента и делает поведение API предсказуемым.

**Graceful degradation для AI.**

Интеграция с AI рассматривается как дополнительная возможность приложения.

Если AI-сервис временно недоступен, обращение пользователя всё равно будет принято, а ответ будет сформирован без AI-резюме.

При этом отправка электронной почты и сохранение данных в базе являются обязательными этапами обработки обращения. Если один из этих компонентов недоступен, запрос завершается ошибкой, поскольку дальнейшая обработка невозможна.

### Пайплайн обращения

```text
POST /api/contact
  1) Pydantic преобразует и валидирует поля формы
  2) Rate limit смотрит IP в data/rate_limit.json
  3) AI пытается классифицировать, оценить тональность и составить ответ
  4) SMTP отправляет письмо владельцу и копию пользователю (одна сессия)
  5) ContactRepository сохраняет данные в таблицу contact_submissions БД
     (имя, контакты, флаги email_sent/ai_available, category, sentiment, suggested_reply, IP)
  6) Клиенту возвращается 201 и ContactResponse
```

Шаг 5 — это не "логирование", а полноценная запись обращения в PostgreSQL. Именно по этим строкам потом считает `/api/metrics`.

## Архитектурные решения

1. **Многослойная архитектура**
   - `api/routers` — входная точка HTTP
   - `schemas` — валидация и сериализация (Pydantic)
   - `services` — сценарии и правила
   - `repositories` — доступ к Postgres / JSON-файлу
   - `models` — ORM-таблицы

2. **Repository Pattern** — сервисы не пишут сырой SQL вперемешку с бизнес-логикой; работа с БД сосредоточена в репозитории.

3. **Service Layer + Dependency Injection** — роутеры тонкие, логику проще покрывать unit-тестами, зависимости подменяются в pytest через `dependency_overrides`.

4. **Pydantic на границе API** — отдельные request/response-модели (`ContactRequest`, `ContactResponse`, `MetricsResponse`, `ErrorResponse`)].

5. **Async SQLAlchemy** — запросы к Postgres не блокируют event loop Uvicorn.

6. **Два способа задать БД** — локально удобны `DB_*`, на Render приходит готовый `DATABASE_URL`; код приводит URL к asyncpg/psycopg2.

7. **Файловый fixed-window rate limit** — простой антиспам без Redis; лимит применяется только к `POST /api/contact`.

8. **Атомарная отправка двух писем в одной SMTP-сессии** — либо оба ушли, либо ошибка считается общей.

9. **AI как необязательное обогащение** — три независимые функции, частичный успех допустим, падение AI не даёт 502.

10. **Централизованные exception handlers** — доменные ошибки (`AppError`, `ExternalServiceError`, `RateLimitError`) и ошибки валидации приводятся к одному JSON-формату.

11. **Разделение логов** — общие события приложения и отдельный access-лог HTTP с `X-Request-ID`.

12. **OpenAPI из коробки FastAPI** — теги, описания, примеры в схемах, UI на `/api/docs`.

13. **Контейнеризация** — Docker-образ + `start.sh` (миграции, запуск сервера) для Render.

14. **Alembic** — схема БД меняется миграциями.

15. **Конфиг через окружение** — `pydantic-settings` + `.env` / переменные Render.

16. **Типизация и линтеры** — аннотации, Ruff/mypy, pre-commit для дисциплины кода.

17. **Health-check** — `/api/health` для мониторинга.

## 4. Реализация API

Префикс API: `/api`. Интерактивная документация: `/api/docs`.

### Эндпоинты

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/` | HTML-лендинг с формой |
| `GET` | `/api/health` | Проверка, что процесс жив |
| `POST` | `/api/contact` | Приём обращения |
| `GET` | `/api/metrics` | Сводная статистика из БД |

### Примеры

**Health — 200**

```http
GET /api/health
```

```json
{
  "status": "ok",
  "service": "StackView",
  "environment": "development"
}
```

**Успешная отправка формы — 201**

```bash
curl -s -X POST http://127.0.0.1:8000/api/contact \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Иван Иванов",
    "phone": "+79991234567",
    "email": "ivan@example.com",
    "comment": "Хочу обсудить проект по FastAPI"
  }'
```

```json
{
  "status": "accepted",
  "message": "Обращение принято",
  "name": "Иван Иванов",
  "phone": "+79991234567",
  "email": "ivan@example.com",
  "comment": "Хочу обсудить проект по FastAPI",
  "email_sent": true,
  "ai_available": true,
  "ai_analysis": {
    "category": "collaboration",
    "category_label": "Сотрудничество",
    "sentiment": "positive",
    "sentiment_score": 0.75
  },
  "suggested_reply": "Спасибо за обращение! ..."
}
```

**Ошибка валидации — 422** (`validation_error`)

Например, некорректный формат email или телефон с недостаточным числом цифр. В `details` — список проблем по полям; фронтенд подсвечивает соответствующие input.

**Слишком много запросов с одного IP — 429** (`rate_limit_exceeded`)

Сервер отвечает roughly: "лимит исчерпан, подождите". В `details` есть сведения о лимите/окне. Это защита формы от простого спама.

**Проблема с почтой или базой — 502**

| `code` | Когда |
|--------|--------|
| `email_not_configured` | В `production` не задан SMTP |
| `email_send_failed` | SMTP настроен, но отправка упала (сеть, логин, timeout на Render Free) |
| `database_error` | Не удалось сохранить обращение в PostgreSQL |

### Валидация и обработка ошибок

На входе `ContactRequest` делает больше, чем «просто проверить типы»:

| Поле | Правила |
|------|---------|
| `name` | обязательно, длина 2–100; HTML-теги удаляются, пробелы нормализуются |
| `comment` | обязательно, длина 1–2000; та же санитизация |
| `email` | формат email через `EmailStr` |
| `phone` | строка нормализуется к цифрам (и опциональному `+`); затем проверка, что цифр от 10 до 15; также ограничение длины сырой строки |

Дополнительно:

- другие/неизвестные ситуации на уровне HTTP ловятся handlers в `exception_handlers.py`
- `ValueError` из кастомного валидатора телефона безопасно попадает в JSON 422 (контекст ошибки очищается от несериализуемых объектов)
- в ответе об ошибке единый контракт `ErrorResponse`

### Про статус-коды

Коды выбраны по смыслу для клиента:

- **201** — обращение успешно принято и обработано пайплайном (создание новой записи сценария)
- **422** — клиент прислал данные, которые нельзя принять (ошибка в полях формы)
- **429** — клиент слишком часто бьёт в форму; нужно подождать
- **502** — сам запрос в целом понятен, но внешняя обязательная часть (почта или БД) не сработала

4xx — "проблема на стороне клиента/лимита", 5xx — "сервер не смог завершить обязательный шаг".

## 5. AI-интеграция

### Инструменты

Используется официальная библиотека **openai**. Через неё приложение вызывает chat completions у провайдера (в демо — Groq).

Три отдельные операции:

| Метод | Что делает |
|-------|------------|
| `classify_request` | Определяет тип обращения: работа, сотрудничество, вопрос или другое |
| `analyze_sentiment` | Оценивает тональность: positive / neutral / negative и числовую оценку от **-1** (очень негативно) до **+1** (очень позитивно) |
| `generate_suggested_reply` | Пишет короткий вежливый черновик ответа на русском |

### Как это запускается по шагам

Метод `AIService.enrich` выступает "дирижёром":

1. Одновременно (параллельно) запускаются классификация и анализ тональности — они не зависят друг от друга, так быстрее.
2. Когда они завершились (успешно или с ошибкой), запускается генерация черновика ответа. В промпт reply по возможности добавляются уже известные категория и тональность — ответ получается осмысленнее.
3. Из того, что удалось, собирается `AIEnrichment` для письма владельцу и для JSON-ответа API / записи в БД.

### Fallback (если AI недоступен или частично сломался)

Идея: **форма важнее модели**.

- Нет API-ключа или `AI_ENABLED=false` — обогащение не вызывается. Пользователь всё равно получает принятие формы, в ответе `ai_available: false`, поля AI пустые.
- Упала только классификация — тональность и/или reply всё ещё могут пройти.
- Упал только reply — в ответе могут остаться category/sentiment.
- Если не удалось ничего — `ai_available: false`.
- Если удалось хотя бы что-то одно — `ai_available: true`, в `ai_analysis` только успешные поля.
- Из-за AI **не бывает** HTTP 502: сбой модели превращается в "нет данных", а не в аварию всего запроса.

Каждый вызов к модели ограничен по времени (`AI_TIMEOUT_SECONDS`, внутри `asyncio.wait_for`), чтобы зависший провайдер не держал форму бесконечно.

### Промпты приложения

Файл: `app/core/ai_prompts.py`.

Там же словарь **`CATEGORY_LABELS`**: соответствие кода категории человекочитаемой подписи на русском, например `job` → "Вакансия / работа". Модель может вернуть свой `category_label`, но если его нет или category неизвестна, сервис подставляет значение из этого словаря (и при необходимости схлопывает category в `other`).

## 7. Хранение данных

| Что | Где | Как устроено                                                                                          |
|-----|-----|-------------------------------------------------------------------------------------------------------|
| Обращения | PostgreSQL, таблица `contact_submissions` | После успешной отправки писем `ContactRepository` делает INSERT данных (контакты, флаги, поля AI, IP) |
| Метрики | та же БД | `GET /api/metrics` считает агрегаты SQL                                                               |
| Rate limit | файл `data/rate_limit.json` | счётчики по IP на окне времени                                                                        |
| Логи приложения | `logs/app.log` (+ консоль) | старт, сервисы, ошибки бизнес-логики                                                                  |
| Логи HTTP | `logs/requests.log` | каждый запрос: method, path, status, длительность, IP, `request_id`                                   |

**Rotating file** — ротация логов по размеру, чтобы диск не забивался одним гигантским файлом. В коде (`app/core/logging.py`):

Когда `app.log` достигает ~2 МБ, он переименовывается в резервную копию, запись идёт в новый файл. То же для `requests.log`.

**Что пишется в HTTP-лог.** Связка: `request_id` (его же отдаёт заголовок `X-Request-ID`), метод, путь, статус, время в мс, IP. При необработанном исключении — запись со status=500.

**Почему используются и файлы, и Postgres.** Обращения и статистика должны переживать перезапуск и попадать в метрики — для этого Postgres. Rate limit и логи в учебном демо удобнее файлами: не нужен Redis, файл можно открыть в редакторе и быстро отладить. На более серьёзной нагрузке rate limit рекомендую вынести в **Redis**, а логи — в сборщик вроде **Grafana Loki**.

## Деплой (Render)

Публичный инстанс: **https://stackview-api.onrender.com**

В репозитории три согласованных артефакта:

1. **`Dockerfile`**
   - база `python:3.12-slim`;
   - ставится Poetry, `POETRY_VIRTUALENVS_CREATE=false`;
   - сначала копируются `pyproject.toml` / `poetry.lock` и ставятся зависимости (кэш слоя);
   - затем копируются `app/`, `alembic/`, `alembic.ini`;
   - `.env` и секреты в образ не попадают (см. `.dockerignore`);
   - точка входа — `scripts/start.sh`.

2. **`scripts/start.sh`**
   - `set -e` — любая ошибка останавливает контейнер;
   - сначала `alembic upgrade head` (схема Postgres должна совпасть с кодом);
   - затем `uvicorn app.main:app --host 0.0.0.0 --port $PORT` (порт задаёт Render).

3. **`render.yaml`**
   - free web-сервис на Docker + free Postgres;
   - `DATABASE_URL` связывается с БД;
   - health check на `/api/health`;
   - SMTP и `OPENAI_API_KEY` задаются вручную в dashboard (не хранятся в git).

Ограничения Free: сервис "засыпает" после простоя; исходящий SMTP на 465/587 часто недоступен — письма надёжнее проверять **локально**.

## Возможные улучшения

- **Деплой с почтой** — VPS либо провайдер писем по HTTP API (Resend, Mailgun), чтобы не упираться в блок SMTP на free-хостинге.
- **Rate limit в Redis** — если запущено несколько копий приложения: файловый JSON между репликами не шарится.
- **Очередь на email/AI** (Celery) — быстрый ответ `POST /api/contact`, тяжёлая работа в фоне.
- **Сбор логов** — **Loki**, **Vector → ClickHouse**, с корреляцией по `request_id`.
- **Метрики** — Prometheus в дополнение к SQL `/api/metrics`.
- **Безопасность** — более строгий CORS, captcha.
- **CI** — GitHub Actions: lint + pytest на каждый PR; отдельный staging.
- **Отдельный фронтенд**, если понадобится более сложный UI при том же API.
